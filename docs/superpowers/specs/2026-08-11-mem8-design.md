# mem8 — Design

**Date:** 2026-08-11
**Status:** Approved

## Purpose

A simple, fast persistent memory for AI coding agents. Claude Code (or any MCP
client) stores what it learns during a session and retrieves it in later
sessions, scoped to the project it is working in.

## Goals

- Zero-setup default: install one binary, add one MCP server entry, done.
- Fast: sub-millisecond search at the scale of thousands of memories per project.
- Agent-controlled: the agent decides what is worth remembering. Nothing is
  extracted automatically.
- Portable: memories can be exported to markdown and imported back.

## Non-goals (v1)

- Vector or semantic search. The schema reserves space for it; no vector code
  ships in v1.
- Automatic memory extraction from conversation transcripts.
- Multi-user access control or memory sharing between users.
- Web UI or any interface beyond MCP and the CLI.

## Decisions

| Decision | Choice | Rationale |
|---|---|---|
| Access | MCP server | Works in Claude Code, Cursor, any MCP client, with no per-client integration. |
| Search | Keyword (FTS5 / tsvector) first, vector later | No API key, no network, no model dependency. Deterministic and fast. |
| Storage | Adapter: SQLite default, Postgres opt-in | Zero-setup default without foreclosing pgvector and multi-machine use. |
| Truth | Database, with export/import | One source of truth; markdown export provides readability and backup without a sync burden. |
| Scoping | Auto-detect, with override and global flag | Costs the agent nothing on the normal path; cross-project lookup stays possible. |
| Memory shape | Content + closed kind set + optional tags | Filterable without the shape rot that freeform metadata invites. |
| Writes | Agent-explicit only | Predictable. Session hooks can be added later without schema or tool changes. |
| Language | Rust | Single static binary, fast startup, mature SQLite and Postgres crates. |

### Verified during design

`rmcp` is the official Rust MCP SDK (`modelcontextprotocol/rust-sdk`), with
roughly 4.7 million crates.io downloads as of early 2026. It tracks the
2026-07-28 specification and remains compatible with 2025-11-25 and earlier. Its
ergonomics are suitable: `#[tool_router(server_handler)]` and `#[tool]` on plain
methods, parameters via `Parameters<T>` with schemas derived by `schemars`,
returns via `Json<T>`, and stdio transport through `serve_server`.

The exact published version was not confirmed — crates.io renders its package
metadata client-side and the fetch returned an empty shell. Pin the version with
`cargo add rmcp` at implementation time.

`sqlite-vec` (for the eventual SQLite vector path) was **not** verified. It must
be checked before v2 work begins. It is brute-force rather than ANN-indexed,
which is acceptable at the expected scale but is a known ceiling.

## Architecture

A single binary with two entry points sharing one core:

```
mem8 serve          → MCP server over stdio (spawned by the MCP client)
mem8 export <path>  → write memories to markdown
mem8 import <path>  → read memories from markdown
```

Four layers, with dependencies flowing in one direction:

```
  mcp/     rmcp tool handlers. Thin: parse arguments, call core, format replies.
    ↓
  core/    Memory logic: scope resolution, validation, ranking.
    ↓
  store/   trait Store, with two implementations.
    ↓
  SqliteStore (default) | PgStore (opt-in)
```

`core` contains no SQL. `store` contains no MCP types. Changing the backend or
adding vector search touches exactly one layer.

The backend is selected at startup from `MEM8_DB`:

- unset → SQLite at `~/.mem8/mem8.db`
- `sqlite:///path` → SQLite at that path
- `postgres://...` → Postgres

### Crates

- `rmcp` — MCP server and stdio transport
- `rusqlite` with the `bundled` feature — SQLite with FTS5, no system dependency
- `sqlx` — Postgres backend
- `thiserror` — error types
- `schemars` / `serde` — tool parameter schemas
- `uuid`, `chrono` — identifiers and timestamps

## Data model

One entity:

```rust
struct Memory {
    id: Uuid,
    project: String,
    kind: Kind,
    content: String,
    tags: Vec<String>,
    created_at: DateTime<Utc>,
    updated_at: DateTime<Utc>,
    embedding: Option<Vec<f32>>,  // reserved; always NULL in v1
}

enum Kind { Decision, Preference, Convention, Fact, Learning }
```

`Kind` is a closed set. Open sets rot: no two writes agree on shape, and filters
stop working.

### SQLite schema

```sql
CREATE TABLE memories (
    id          TEXT PRIMARY KEY,
    project     TEXT NOT NULL,
    kind        TEXT NOT NULL,
    content     TEXT NOT NULL,
    tags        TEXT NOT NULL DEFAULT '[]',   -- JSON array
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL,
    embedding   BLOB                          -- reserved; NULL in v1
);
CREATE INDEX idx_project ON memories(project);
CREATE INDEX idx_project_kind ON memories(project, kind);

CREATE VIRTUAL TABLE memories_fts USING fts5(
    content,
    content='memories',
    content_rowid='rowid'
);
```

FTS5 runs in external-content mode, so text is not duplicated. Three triggers
(insert, update, delete) keep the index synchronised with the base table.

### Postgres schema

The same columns using native types: `uuid`, `text[]` for tags, `timestamptz`,
and a `vector` column when vector search arrives. Search uses `tsvector` with a
GIN index rather than FTS5. The `Store` trait hides the difference; both
implementations return `Vec<String>` for tags regardless of storage encoding.

### Migrations

Migrations run automatically at startup and are forward-only; v1 has no
rollback. A database newer than the binary is a startup error naming the version
gap, not a mid-request failure.

## MCP tool surface

Five tools. The surface is deliberately small — every tool costs agent context
in every session.

### `add_memory`

```
content: string     required
kind:    enum       required (decision|preference|convention|fact|learning)
tags:    string[]   optional
project: string     optional, overrides auto-detected scope
→ { id, project, kind }
```

### `search_memory`

```
query:   string     required, FTS match
kind:    enum       optional filter
tags:    string[]   optional filter, AND semantics
project: string     optional scope override
global:  bool       optional, default false — search across all projects
limit:   int        optional, default 10, maximum 50
→ [ { id, project, kind, content, tags, created_at, score } ]
```

### `get_memory`

```
id: string          required
→ full Memory
```

For following up on a search result.

### `update_memory`

```
id:      string     required
content: string     optional
kind:    enum       optional
tags:    string[]   optional
→ updated Memory
```

Bumps `updated_at`. Facts change; rewriting a memory beats accumulating
contradictory ones.

### `delete_memory`

```
id: string          required
→ confirmation
```

A wrong memory is worse than no memory.

### Scope resolution

Resolved in order:

1. Explicit `project` parameter
2. Basename of the git root containing the working directory
3. Basename of the working directory

`global: true` skips scope filtering entirely.

## Error handling

`core` defines a `Mem8Error` enum via `thiserror`, mapped to `rmcp` error
responses at the MCP boundary. `store` errors wrap backend failures without
leaking `rusqlite` or `sqlx` types upward.

| Class | Behaviour |
|---|---|
| Invalid input (unknown kind, `limit` over 50, empty content, malformed FTS query) | Tool error whose message states how to correct the call. Never a panic. |
| Memory not found | Explicit not-found error, never silent success — agents may hold identifiers deleted in an earlier session. |
| Store unavailable (unwritable file, Postgres down, dropped connection) | Error returned to the agent; the server stays alive so the session continues without memory. |
| Schema mismatch | Startup failure naming the version gap. |
| Scope detection failure | Fall back to the working-directory basename, then to `"default"`. Never blocks a write. |

FTS query strings reach a real parser, so unbalanced quotes and stray operators
must be sanitised in `core` before they are handed to the store.

Panics are reserved for genuine invariant violations and must not be reachable
from agent input.

## Testing

Tests are written before the implementation they cover, layer by layer.

**Store contract tests.** One suite written against `trait Store`, executed once
per implementation. Identical assertions across both backends catch divergence
in tag encoding, timestamp precision, and result ordering. SQLite runs
in-memory. Postgres tests are feature-gated behind `MEM8_TEST_PG` so that a
plain `cargo test` requires no running server.

**Core unit tests.** Run against an in-memory `Vec<Memory>` implementation of
`Store`. Cover scope resolution (git root, working-directory fallback, explicit
override, global), kind and limit validation, FTS query sanitising, and
not-found paths.

**MCP tool-surface tests.** Handlers invoked with real JSON arguments, asserting
schema shape and error mapping. These catch the case where an agent sends
plausible arguments and receives a panic.

**End-to-end tests.** Spawn the binary, perform a real MCP handshake over stdio,
call `add_memory` followed by `search_memory`, and assert the round trip. Few in
number and slow, but the only tests that prove the wire contract.

**CLI round-trip test.** `export` followed by `import` must reproduce an
identical memory set. This is what keeps the markdown format honest.

## Deferred to v2

- Vector search. SQLite via `sqlite-vec` (verify first) or Postgres via
  pgvector. The `embedding` column and the single search entry point in `core`
  exist so this lands without changing the tool surface.
- Session-end hooks that prompt the agent to record what mattered.
- Deduplication and consolidation of overlapping memories.
